LiveKit IPC 安全技术深度解析

从密码学原理到工程实现，逐层拆解 WebRTC 实时通信中的六层安全机制。讲清楚每层"为什么安全"、"怎么做到的"、"代码在哪里"。

WebRTC DTLS-SRTP ICE/STUN/TURN HMAC-SHA256 AES-128-CTR ECDSA P-256 mbedTLS

全文概览

当你用手机 App 看到家里的 IPC 摄像头画面时，视频数据经过了这样一个路径：

IPC 摄像头 ──UDP──→ 路由器/NAT ──UDP──→ TURN 中继 ──UDP──→ LiveKit SFU ──UDP──→ 手机 App 问题：这条路径上每个环节都可能被窃听、篡改、伪造。如何保证： 1. 只有授权设备能推流？ → JWT 认证 2. 控制命令不被窃听？ → WSS (TLS 1.2) 3. 网络探测消息不被伪造？ → ICE 认证 (HMAC) 4. 媒体密钥不被泄露？ → DTLS 握手 (ECDHE) 5. DTLS 证书不被替换？ → SDP 指纹绑定 (SHA-256) 6. 视频流不被窃听？ → SRTP 加密 (AES-128)

这 6 层安全机制不是简单堆叠，而是形成一个信任链：每一层为下一层提供信任根基，缺少任何一层都会导致整条链路的安全性崩溃。

安全全景图

LiveKit IPC 通信有且仅有两条通道，安全机制分别守护：

通道协议传输内容安全机制保护目标
信令通道WebSocket over TLSJWT、SDP、ICE 候选、控制消息JWT 认证 + TLS 1.2 加密身份 + 机密性

信任模型

理解安全的关键在于理解信任从哪里来。WebRTC 使用了一种与传统 HTTPS 完全不同的信任模型：

传统 Web (HTTPS)

信任根：CA 证书链（DigiCert、Let's Encrypt 等）

验证方式：浏览器内置 CA 根证书，验证服务器证书是否由可信 CA 签发

前提：CA 是可信第三方

问题：IPC 设备不可能每个都申请 CA 证书；嵌入式设备无法维护 CA 证书库

WebRTC (DTLS-SRTP)

信任根：信令通道（已受 TLS 保护）

验证方式：通过信令通道传递证书 SHA-256 指纹，DTLS 握手后比对指纹

前提：信令通道是安全的（由 TLS 保证）

优势：自签名证书足够安全，无需 CA，适合嵌入式设备

核心洞察
WebRTC 安全的本质是：用信令通道的安全来保证媒体通道的安全。信令通道通过 TLS + JWT 保护，然后在信令通道中传递 DTLS 证书指纹，媒体通道的证书验证就不再依赖 CA，而是依赖信令通道传递的指纹。这就是为什么 6 层安全是一根链条，而不是简单堆叠。

密码学核心概念

在逐层讲解安全机制之前，先搞清楚底层用到的密码学原语。这 6 层安全只用到了 5 种密码学原语：

原语算法用途出现在哪层
哈希SHA-256, SHA-1数据指纹，不可逆第5层 (SHA-256), 证书签名 (SHA-1)
HMACHMAC-SHA256, HMAC-SHA1消息认证码，防篡改+验证身份第1层 (SHA256), 第3层 (SHA1), 第6层 (SHA1)
对称加密AES-128-CTR, AES-128-GCM加密数据，加解密用同一密钥第2层 (GCM), 第6层 (CTR)
非对称加密ECDHE, ECDSA密钥交换、数字签名第2层 (ECDHE), 第4层 (ECDHE+ECDSA)
随机数CTR-DRBG生成不可预测的密钥材料所有层

哈希与 HMAC

哈希函数 (Hash)

哈希函数把任意长度的数据映射为固定长度的"指纹"。关键性质：

  • 单向性：从哈希值无法反推原始数据
  • 抗碰撞性：找不到两个不同数据产生相同哈希值
  • 雪崩效应：输入改变 1 bit，输出变化约 50%
// SHA-256: 输入任意长度 → 输出 256 bit (32 字节)
SHA-256("hello") = 2cf24dba5fb0a30e26e83b2ac5b9e29e1b161e5c1fa7425e73043362938b9824
SHA-256("hellp") = d1b2a59fbea7e20077af9f96539fe2cfeb1e675b0036b8b4baee9c6fa29e6e21
                                    ↑ 只改了 1 个字母，输出完全不同

HMAC (Hash-based Message Authentication Code)

HMAC = 哈希 + 密钥。它解决的问题是：怎么证明消息没被篡改，而且确实来自持有密钥的人。

// HMAC-SHA256 的计算方式
HMAC-SHA256(key, message) = SHA-256(
    (key XOR opad) || SHA-256((key XOR ipad) || message)
)

// 验证方用相同的 key 重新计算，比对结果
// 没有密钥的人无法生成正确的 HMAC → 无法伪造
// 修改消息会导致 HMAC 不匹配 → 篡改被发现
哈希 vs HMAC

哈希只能告诉你"数据是否被修改"，但不能告诉你"谁修改的"。 HMAC加了一层密钥保护，既能检测篡改，又能验证消息来源（因为只有持有密钥的人才能生成正确的 HMAC）。在 LiveKit 中，JWT 签名用 HMAC-SHA256，STUN 消息认证用 HMAC-SHA1，SRTP 认证也用 HMAC-SHA1。

对称加密

对称加密：加密和解密用同一个密钥。优点是速度快，缺点是密钥必须安全地分享给对方。

// AES-128-CTR 模式 (用于 SRTP)
密钥: 16 字节 (128 bit)
加密: Ciphertext = AES_CTR(Plaintext, Key, IV)
解密: Plaintext  = AES_CTR(Ciphertext, Key, IV)
// 加密和解密是同一个操作 (CTR 模式的特性)

// AES-128-GCM 模式 (用于 TLS)
// GCM = CTR 加密 + GHASH 认证，同时提供机密性和完整性
// 比 CTR + HMAC 更高效 (一次遍历同时加密和认证)
CTR vs GCM

CTR 模式只提供加密，不提供完整性验证，需要额外加 HMAC。GCM 模式是 CTR + 认证一体化，更现代更高效。SRTP 用 CTR+HMAC（因为 SRTP 协议设计时 GCM 还不成熟），TLS 用 GCM（更现代的选择）。

非对称加密与密钥交换

非对称加密用一对密钥：公钥（公开）和私钥（保密）。

算法类型用途在本项目中的作用
ECDHE密钥交换双方在不安全通道上协商出共享密钥TLS 握手、DTLS 握手中协商会话密钥
ECDSA数字签名私钥签名，公钥验证DTLS 证书签名、TLS 服务器证书验证

ECDHE 密钥交换原理

// ECDHE (Elliptic Curve Diffie-Hellman Ephemeral)
// 两条线各生成临时密钥对，交换公钥，各自算出相同的共享密钥

板端:                                    服务器:
  随机生成 a (私钥)                        随机生成 b (私钥)
  计算A = G * a (公钥)                     计算B = G * b (公钥)
           ──── A ────→
           ←─── B ─────
  共享密钥 = B * a                        共享密钥 = A * b
           (= G * a * b)                  (= G * b * a)
           ↑ 两边结果相同！窃听者只有 A 和 B，算不出 a*b

// "Ephemeral" = 每次会话重新生成，保证前向保密 (PFS)
// 即使以后私钥泄露，历史会话密钥也无法推导
前向保密 (PFS)
ECDHE 的 "E" 代表 Ephemeral（临时的）。每次连接都生成新的临时密钥对，会话结束后销毁。这意味着：即使今天服务器被攻破、私钥泄露，攻击者也无法解密之前录制的任何会话。这是 WebRTC 安全的关键属性。

数字签名与证书

数字签名 = 非对称加密 + 哈希。用来证明"这条消息确实是由私钥持有者发出的，且未被篡改"。

// 签名过程
签名 = ECDSA_Sign(私钥, SHA-256(消息))

// 验证过程
ECDSA_Verify(公钥, SHA-256(消息), 签名) → true/false

// 数字证书 = 公钥 + 身份信息 + CA 签名
// 在 WebRTC 中：自签名证书 + SDP 指纹 = 等效 CA 验证

随机数生成

所有密码学都依赖随机数。如果随机数可预测，密钥就可推导，一切安全机制失效。

// 板端随机数生成链路 (Dtls_mbedtls.c)
mbedtls_entropy_init()           // 初始化熵收集器
mbedtls_ctr_drbg_init()         // 初始化 CTR-DRBG 伪随机数生成器
mbedtls_ctr_drbg_set_prediction_resistance(ON)  // 启用预测抵抗
mbedtls_ctr_drbg_seed(entropy_func, ...)        // 用 /dev/urandom 的熵做种子

// CTR-DRBG: NIST SP 800-90A 标准算法
// prediction resistance: 每次取随机数前重新收集熵
// 熵源: /dev/urandom (Linux 内核 RNG)
嵌入式设备的随机数风险
嵌入式设备在启动早期，/dev/urandom 的熵可能不足（缺少用户输入、磁盘 IO 等熵源）。如果在此阶段生成密钥，可能产生可预测的随机数。量产前应验证板端 /dev/urandom 在启动各阶段的熵质量。

第1层 — JWT 认证

要解决的问题

LiveKit SFU 需要回答："你是谁？你有权做什么？" JWT (JSON Web Token) 就是身份证明。

JWT 结构

// JWT = Header.Payload.Signature，三段用 "." 连接

Header:  {"alg":"HS256","typ":"JWT"}                  // 算法声明
Payload: {"iss":"APIuaW8TWYjHf63",                    // 签发者 = API Key
          "sub":"testpub",                             // 主体 = 设备身份
          "exp":1779437486,                             // 过期时间
          "nbf":1779347486,                             // 生效时间
          "video":{"canPublish":true,                   // 可推流
                   "canSubscribe":false,                // 不可订阅
                   "room":"test",                       // 房间名
                   "roomJoin":true}}                    // 可加入
Signature: HMAC-SHA256(                                // 签名 = 认证码
    base64url(Header) + "." + base64url(Payload),
    API_SECRET                                        // 密钥 = API Secret
)

为什么 JWT 不可伪造？

1
API Secret 是信任根
API Secret 只存在于你的后端服务器和 LiveKit Cloud，从不通过网络传输。后端用它签发 JWT，SFU 用它验证 JWT。
2
HMAC 保证完整性
攻击者没有 API Secret，无法为篡改后的 Payload 生成正确的 HMAC。SFU 验证签名不匹配就直接拒绝。
3
exp/nbf 保证时效性
过期 token 被 SFU 拒绝。攻击者拿到一个旧 token 也没用。
4
最小权限保证隔离
IPC 设备的 token 设置 canPublish: true, canSubscribe: false，只能推流不能订阅其他流。即使 token 泄露，攻击者也无法通过这个 token 看到其他设备的视频。

代码实现

JWT 在板端通过 WebSocket URL 的 query string 传递：

// LiveKitSignaling.cpp:386
m_impl->wsPath += "access_token=" + config.token;
m_impl->wsPath += "&protocol=" + std::to_string(SIGNAL_PROTOCOL_VERSION);

// 最终 URL 形如:
// wss://pawrtc-qbbhiyec.livekit.cloud/rtc?access_token=eyJ...&protocol=17
风险：JWT 在 URL 中传输
JWT 通过 URL query string 传递，可能出现在：(1) 服务器访问日志 (2) CDN 缓存 (3) 浏览器历史记录。虽然 WSS 加密了传输过程，但日志端的泄露风险仍然存在。缓解措施：设置较短的 exp，即使泄露也很快失效。

第2层 — WSS (TLS 1.2) 加密

要解决的问题

信令通道传输 JWT、SDP（含 DTLS 指纹）、ICE 候选等敏感信息。如果明文传输，所有安全机制形同虚设——攻击者可以窃取 JWT 伪造身份，可以篡改 SDP 指纹实施中间人攻击。

TLS 1.2 握手流程

// TLS 1.2 ECDHE 握手（信令通道）
板端 (Client)                           服务器 (Server)
    │                                       │
    │──── ClientHello ────────────────────→ │  支持的密码套件、随机数
    │                                       │
    │←─── ServerHello ───────────────────── │  选定套件、随机数
    │←─── Certificate ──────────────────── │  服务器证书链
    │←─── ServerKeyExchange (ECDHE) ────── │  ECDHE 参数 + 签名
    │←─── ServerHelloDone ──────────────── │
    │                                       │
    │──── ClientKeyExchange (ECDHE) ──────→ │  客户端 ECDHE 公钥
    │──── ChangeCipherSpec ──────────────→ │
    │──── Finished (加密) ────────────────→ │
    │                                       │
    │←─── ChangeCipherSpec ──────────────── │
    │←─── Finished (加密) ───────────────── │
    │                                       │
    │═══════ 应用数据 (WebSocket 帧) ═══════│  双方用协商的密钥加密通信

为什么信令通道是安全的？

安全属性如何实现攻击场景
机密性AES-128-GCM 加密所有数据Wireshark 抓包只能看到密文
完整性GCM 模式自带认证 tag任何篡改都会导致解密失败
身份验证服务器证书 + CA 验证防止连接到伪造服务器
前向保密ECDHE 临时密钥交换服务器私钥泄露不影响历史会话

代码实现

// LiveKitSignaling.cpp — LWS 上下文配置
ctxInfo.options = LWS_SERVER_OPTION_DO_SSL_GLOBAL_INIT;  // 启用 TLS
ctxInfo.client_ssl_ca_filepath = "/etc/ssl/certs/ca-bundle.crt";  // CA 证书
ctxInfo.alpn = "http/1.1";  // 强制 HTTP/1.1，防止 CDN 协商 H2

// Tls_mbedtls.c — 证书验证
// 有 hostname 时：严格验证 (VERIFY_REQUIRED)
mbedtls_ssl_conf_authmode(&sslCtxConfig, MBEDTLS_SSL_VERIFY_REQUIRED);
mbedtls_ssl_set_hostname(&sslCtx, hostname);
// 无 hostname 时：可选验证 (VERIFY_OPTIONAL) — 板端当前走此路径
mbedtls_ssl_conf_authmode(&sslCtxConfig, MBEDTLS_SSL_VERIFY_OPTIONAL);
当前风险：VERIFY_OPTIONAL
板端因为 CA 证书不完整，TLS 验证设为 OPTIONAL。这意味着板端不验证服务器证书的合法性，中间人可以伪造服务器证书拦截信令。修复：推送完整 ca-certificates.crt 后改为 VERIFY_REQUIRED。

ALPN 为什么重要？

LiveKit Cloud 前面有 CDN（如 Cloudflare）。CDN 支持 HTTP/2，如果客户端也支持 H2，TLS 握手时就会协商使用 H2。但 WebSocket 升级需要 HTTP/1.1（RFC 8441 的 H2+WS 支持还不普及），如果走了 H2，WS 升级请求会被拒绝。强制 alpn=http/1.1 确保 CDN 不会协商 H2。

第3层 — ICE 认证

要解决的问题

ICE (Interactive Connectivity Establishment) 通过 STUN/TURN 协议在 UDP 上做 NAT 穿透。如果攻击者能伪造 STUN 消息，就可以劫持 ICE 连接，把媒体流发到错误的目的地。ICE 认证防止这种情况。

两种认证机制

STUN 短期凭证

用途：ICE 连通性检查（Binding Request/Response）

凭证来源：SDP 中的 a=ice-ufrag 和 a=ice-pwd

生命周期：一个 ICE 会话（几分钟到几小时）

验证方式：HMAC-SHA1(ice-pwd, message) → MESSAGE-INTEGRITY

TURN 长期凭证

用途：TURN 服务器认证（Allocate/Refresh）

凭证来源：LiveKit Cloud 在 JoinResponse 中动态下发

生命周期：一个 TURN Allocation

验证方式：MD5(MD5(user:realm:pass):nonce:md5_hash)

STUN 短期凭证详解

// SDP 中交换的凭证（明文，但受 TLS 保护）
a=ice-ufrag:4aHMxe4V              // 用户名片段，随机生成
a=ice-pwd:5qUzIr4WgQ7T5xRcsCyTZOEF  // 密码，随机生成

// STUN Binding Request 携带认证信息
STUN Binding Request:
  USERNAME: "KXfxYlfOdnPeKSWc:4aHMxe4V"    // remote_ufrag:local_ufrag
  MESSAGE-INTEGRITY: HMAC-SHA1(ice-pwd, entire_message)  // 20 字节
  FINGERPRINT: CRC32(entire_message)                      // 4 字节

// 验证流程:
// 1. 接收方用 SDP 中的 ice-pwd 重新计算 HMAC-SHA1
// 2. 与 MESSAGE-INTEGRITY 比对 → 不匹配则丢弃
// 3. CRC32 FINGERPRINT 检测 NAT/中间盒对 STUN 消息的篡改

TURN 长期凭证详解

// TURN Allocate 流程 (RFC 5389 长期凭证)
板端 → TURN:  Allocate Request (无 MESSAGE-INTEGRITY)     // 第1次：无认证
TURN → 板端:   401 Unauthorized (REALM + NONCE)            // 挑战：给你 realm 和 nonce
板端 → TURN:  Allocate Request (含 MESSAGE-INTEGRITY)     // 第2次：带认证
TURN → 板端:   Allocate Success Response                   // 认证通过，分配中继

// 认证计算:
md5_hash = MD5(username + ":" + realm + ":" + password)  // 长期哈希
MESSAGE-INTEGRITY = HMAC-SHA1(md5_hash, nonce + message)    // 用长期哈希做 HMAC

// 安全属性:
// - REALM + NONCE 防止重放: 每次挑战的 nonce 不同
// - 密码不以明文传输: 只传 MD5 哈希 + HMAC
// - TURN 凭证由 Cloud 动态下发: 每个会话不同

第4层 — DTLS 握手

要解决的问题

SRTP 需要密钥来加解密媒体数据。问题是：怎么在不安全的 UDP 通道上安全地协商出密钥？ DTLS (Datagram TLS) 就是答案——它在 UDP 上完成 TLS 握手，协商出密钥，然后导出给 SRTP 使用。

DTLS 为什么是核心枢纽？

DTLS 的核心地位
DTLS 是整条安全链路的密钥来源。JWT 验证身份，TLS 保护信令，ICE 建立连接，SDP 传递指纹——这一切的最终目的是让 DTLS 安全地完成握手，导出 SRTP 密钥。没有 DTLS，SRTP 就没有密钥，媒体数据就是明文。

DTLS 证书生成

DTLS 需要证书。WebRTC 不用 CA 签发的证书，而是每次启动时动态生成自签名证书：

// Dtls_mbedtls.c:694 — createCertificateAndKey()

// 1. 生成随机序列号 (防预测)
BYTE certSn[DTLS_CERT_MAX_SERIAL_NUM_SIZE];  // 20 字节
dtlsFillPseudoRandomBits(certSn, SIZEOF(certSn));

// 2. 生成 ECDSA P-256 密钥对
mbedtls_pk_setup(pKey, mbedtls_pk_info_from_type(MBEDTLS_PK_ECKEY));
mbedtls_ecp_gen_key(MBEDTLS_ECP_DP_SECP256R1, ...);  // 256-bit 椭圆曲线

// 3. 生成自签名证书
mbedtls_x509write_crt_set_version(pWriteCert, MBEDTLS_X509_CRT_VERSION_3);
mbedtls_x509write_crt_set_md_alg(pWriteCert, MBEDTLS_MD_SHA1);  // ⚠ SHA-1 签名
mbedtls_x509write_crt_set_validity(pWriteCert, notBefore, notAfter); // 365 天
mbedtls_x509write_crt_set_subject_name(pWriteCert, "O=KVS-WebRTC-Client,CN=KVS-WebRTC-Client");
mbedtls_x509write_crt_set_issuer_name(pWriteCert, "O=KVS-WebRTC-Client,CN=KVS-WebRTC-Client"); // 自签名

DTLS 握手流程

// DTLS 1.2 握手 (基于 UDP)
板端 (DTLS Server)                     SFU (DTLS Client)
    │                                       │
    │←─── ClientHello + SRTP extension ──── │  客户端发起，携带 SRTP profile
    │                                       │
    │──── HelloVerifyRequest ────────────→ │  // ⚠ 本实现跳过 (Cookie 禁用)
    │                                       │
    │──── ServerHello + Certificate ─────→ │  服务端证书 + 选定 SRTP profile
    │──── ServerKeyExchange (ECDHE) ────→ │  ECDHE 参数
    │──── CertificateRequest ───────────→ │  要求客户端提供证书
    │──── ServerHelloDone ──────────────→ │
    │                                       │
    │←─── Certificate ──────────────────── │  客户端证书
    │←─── ClientKeyExchange (ECDHE) ───── │  ECDHE 公钥
    │←─── CertificateVerify ───────────── │  证书签名验证
    │←─── ChangeCipherSpec ───────────── │
    │←─── Finished (加密) ─────────────── │
    │                                       │
    │──── ChangeCipherSpec ──────────────→ │
    │──── Finished (加密) ───────────────→ │
    │                                       │
    │═══ 握手完成，导出 SRTP 密钥 ═════════│
DTLS Cookie 禁用的风险
DTLS Cookie (HelloVerifyRequest) 的作用是防止放大攻击：攻击者伪造源 IP 发送 ClientHello，服务器响应大量数据到受害者 IP。禁用 Cookie 简化了实现，但暴露了放大攻击风险。建议量产时启用。

第5层 — SDP 指纹绑定

要解决的问题

DTLS 握手中，双方交换证书。但问题是：怎么知道收到的证书确实是对方的，而不是中间人替换过的？

传统方案是用 CA 验证，但 WebRTC 不用 CA。WebRTC 的方案是：通过已受 TLS 保护的信令通道，提前传递证书的哈希指纹。

指纹生成

// Dtls_mbedtls.c:809 — dtlsCertificateFingerprint()

// 1. 对证书 DER 编码做 SHA-256 哈希
mbedtls_sha256(pCert->raw.p, pCert->raw.len, fingerprint, 0);

// 2. 格式化为 "XX:XX:XX:..." 形式
// 输出示例:
"1B:0F:43:F8:30:EC:BC:FC:CC:5C:25:17:7F:EE:33:B0:12:33:E2:EE:04:76:B2:39:9E:2D:0E:42:F0:3A:34:6E"

指纹在 SDP 中的传递

// 板端发出的 SDP Offer:
a=fingerprint:sha-256 1B:0F:43:F8:30:EC:BC:FC:CC:5C:25:17:7F:EE:33:B0:...

// SFU 返回的 SDP Answer:
a=fingerprint:sha-256 BB:6F:AD:04:3A:A8:D5:84:89:26:57:F1:60:59:6A:2A:FF:73:DC:...

指纹验证流程

1
信令通道传递指纹
SDP 中的 a=fingerprint:sha-256 ... 通过 WSS (TLS 加密) 传输。攻击者无法在不破坏 TLS 的前提下篡改指纹。
2
DTLS 握手收到证书
DTLS 握手过程中，对端发送其证书。本地获取到证书的原始数据。
3
本地计算指纹
对收到的证书做 SHA-256 哈希，计算其指纹。
4
比对指纹
将计算的指纹与 SDP 中的指纹比对。不匹配则拒绝连接——说明证书被替换了。

代码实现

// Dtls_mbedtls.c:491 — dtlsSessionVerifyRemoteCertificateFingerprint()

// 获取对端证书
pRemoteCertificate = mbedtls_ssl_get_peer_cert(&pDtlsSession->sslCtx);

// 计算对端证书的 SHA-256 指纹
dtlsCertificateFingerprint(pRemoteCertificate, actualFingerprint);

// 与 SDP 中期望的指纹比对
STRCMP(pExpectedFingerprint, actualFingerprint) == 0;
// 不匹配 → STATUS_SSL_REMOTE_CERTIFICATE_VERIFICATION_FAILED
为什么自签名证书足够安全？
传统 HTTPS 依赖 CA 信任链，因为任何人都能生成自签名证书，必须有一个可信第三方来保证"这个证书确实属于这个域名"。但在 WebRTC 中，证书的信任锚不是 CA，而是信令通道中传递的指纹。信令通道受 TLS 保护（不可篡改），指纹就是证书的"身份证"。自签名证书 + 指纹绑定 = 等效 CA 验证，而且更简单。

第6层 — SRTP 媒体加密

要解决的问题

视频和音频数据通过 UDP 传输。如果明文传输，同一网络中的任何人都可以用 Wireshark 抓包看到视频内容。SRTP (Secure RTP) 对每个 RTP 包加密+认证，确保媒体数据的机密性和完整性。

SRTP 加密配置

SRTP Profile: AES128_CM_HMAC_SHA1_80
  ├── 加密: AES-128 Counter Mode (CTR)     ← 机密性
  ├── 认证: HMAC-SHA1 (80-bit auth tag)     ← 完整性
  ├── 密钥: 16 字节 master key + 14 字节 salt = 30 bytes per direction
  └── 重放防护: 滑动窗口 (128 packets)       ← 防重放

SRTP 密钥从哪来？

这是最关键的问题。SRTP 密钥不是自己生成的，而是由 DTLS 握手导出的：

// Dtls_mbedtls.c:518 — dtlsSessionPopulateKeyingMaterial()

// 1. 用 TLS PRF 从 master secret 导出密钥材料
mbedtls_ssl_tls_prf(pKeys->tlsProfile,
    pKeys->masterSecret, ARRAY_SIZE(pKeys->masterSecret),
    KEYING_EXTRACTOR_LABEL,        // "EXTRACTOR-dtls_srtp"
    pKeys->randBytes,              // client_random + server_random
    ARRAY_SIZE(pKeys->randBytes),
    keyingMaterialBuffer,          // 输出: 60 字节
    ARRAY_SIZE(keyingMaterialBuffer));

// 2. 从导出材料中拆分出各方向密钥
// 60 bytes = client_key(16) + server_key(16) + client_salt(14) + server_salt(14)
MEMCPY(pDtlsKeyingMaterial->clientWriteKey,     &buf[0],  16);  // 浏览器→SFU 方向
MEMCPY(pDtlsKeyingMaterial->serverWriteKey,     &buf[16], 16);  // 板端→SFU 方向
MEMCPY(pDtlsKeyingMaterial->clientWriteKey+16,  &buf[32], 14);  // client salt
MEMCPY(pDtlsKeyingMaterial->serverWriteKey+16,  &buf[46], 14);  // server salt

加密流程详解

// 发送端加密 (SrtpSession.c:132)
srtp_protect(ctx, rtp_buf, &len);
  1. 从 RTP 头获取 SSRC 和 sequence number
  2. 计算 IV = (SSRC || ROC || SeqNum || 0x000000) XOR (master_salt)
     // ROC = Roll-Over Counter, 跟踪 seq 溢出
  3. AES-128-CTR 加密 RTP payload
     // CTR 模式: 把 IV 作为计数器输入 AES，输出与明文异或
  4. 计算 HMAC-SHA1 over 整个 RTP 包 (含加密后的 payload)
  5. 附加 10 字节 auth tag

// 接收端解密 (SrtpSession.c:103)
srtp_unprotect(ctx, rtp_buf, &len);
  1. 从 sequence number 计算 ROC
  2. 检查重放窗口 (滑动窗口, 128 packets)
  3. 验证 auth tag (HMAC-SHA1)
  4. 验证通过 → 计算 IV → AES-128-CTR 解密 payload
  5. 验证失败 → 丢弃包

SRTP 包格式

// 原始 RTP 包
[Header 12B][Header Ext ~8B][Payload (H.264 NALU)]

// SRTP 包 (加密后)
[Header 12B][Header Ext ~8B][Encrypted Payload][Auth Tag 10B]
                              ↑ AES-128-CTR 加密         ↑ HMAC-SHA1

// 开销: 每包 +10 字节 auth tag
// 以 1000 字节 MTU、15fps 计算: 10 * 15 * 60 = 9KB/min 额外开销

重放攻击防护

// libsrtp2 滑动窗口 (默认 128 packets)
                     ┌──────────────────────┐
  已收 seq:  ...100 101 102 │ 103 104 105 106 107 │ 108 ...
                     └──────────────────────┘
                     窗口左边界            窗口右边界

  seq > 右边界:  正常接收，窗口右移
  窗口内已收:   重放包，丢弃
  窗口内未收:   可能重传，接受
  seq < 左边界: 太旧，丢弃

信任链分析

6 层安全不是简单堆叠，而是一环扣一环的信任链。每一层为下一层提供信任根基：

API Secret (后端安全存储)
信任根：只有后端知道，从不传输
→
第1层: JWT
API Secret 签发 → SFU 验证 → 确认设备身份和权限
→
第2层: WSS (TLS)
JWT 认证通过后 → TLS 加密信令通道 → SDP/ICE 信息不可篡改
第2层保证 → 第5层
TLS 保护的信令 → SDP 指纹不可篡改 → DTLS 证书不可替换
→
第5层保证 → 第4层
SDP 指纹绑定 → DTLS 握手的证书验证 → 密钥协商安全
→
第4层保证 → 第6层
DTLS 握手安全 → SRTP 密钥安全 → 媒体数据安全
信任链断裂的后果

如果第2层 (TLS) 被攻破（如 VERIFY_OPTIONAL 导致中间人攻击），攻击者可以篡改 SDP 中的指纹，替换为自己的证书指纹。此时第5层失效 → 第4层 DTLS 握手与攻击者建立连接 → 第6层 SRTP 密钥由攻击者掌握 → 所有媒体数据可被解密。一环断裂，全链崩溃。

密钥派生全链路

从最终保护媒体的 SRTP 密钥开始，逆向追溯它的来源：

SRTP 密钥 (每方向 30 bytes) │ │ ← DTLS 握手导出 (dtlsSessionPopulateKeyingMaterial) │ 用 TLS PRF 从 master_secret 派生 │ 标签: "EXTRACTOR-dtls_srtp" │ 输入: master_secret + client_random + server_random │ ├── master_secret (48 bytes) │ │ │ │ ← ECDHE 密钥交换计算 │ │ 板端: shared_secret = B * a (服务器公钥 × 板端私钥) │ │ 服务器: shared_secret = A * b (板端公钥 × 服务器私钥) │ │ → 两侧得到相同的 shared_secret │ │ → master_secret = PRF(shared_secret, randoms) │ │ │ ├── 板端临时私钥 a ← CTR-DRBG (/dev/urandom 熵源) │ └── 服务器临时私钥 b ← 服务器随机数生成器 │ ├── client_random (32 bytes) ← 板端 CTR-DRBG 生成 └── server_random (32 bytes) ← 服务器随机数生成器 最终导出的 60 字节密钥材料: [client_key(16)][server_key(16)][client_salt(14)][server_salt(14)] │ │ │ │ ↓ ↓ ↓ ↓ 板端 receiveKey 板端 transmitKey receiveSalt transmitSalt (解密浏览器数据) (加密板端数据)
前向保密的全链保证
密钥链中所有非对称密钥都是 Ephemeral（临时的）。板端的 a 和服务器的 b 在会话结束后销毁。即使以后 API Secret、服务器长期私钥都泄露，攻击者也无法从录制的流量中推导出历史 SRTP 密钥。这是 ECDHE 的核心价值。

攻击向量分析

从攻击者的角度，逐一分析可能的攻击方式和对应防护：

攻击向量攻击方式防护层防护原理状态
信令窃听 Wireshark 在网络中抓包，获取 JWT、SDP、ICE 候选 第2层: TLS 1.2 AES-128-GCM 加密所有信令数据，ECDHE 保证 PFS 已防护
信令篡改 (MITM) 中间人拦截并修改 SDP 指纹、ICE 候选 第2层: TLS GCM 认证 tag 检测任何篡改，篡改导致解密失败 已防护
伪造设备身份 伪造 JWT 加入房间推流 第1层: JWT 没有 API Secret 无法伪造 HMAC-SHA256 签名 已防护
ICE 消息伪造 伪造 STUN Binding Request 劫持 ICE 连接 第3层: ICE 认证 MESSAGE-INTEGRITY (HMAC-SHA1) 验证，无 ice-pwd 无法伪造 已防护
媒体窃听 Wireshark 抓 RTP 包，尝试解码视频 第6层: SRTP AES-128-CTR 加密，无密钥只能看到密文 已防护
媒体篡改/注入 伪造 RTP 包注入视频流 第6层: SRTP Auth HMAC-SHA1-80 认证，auth tag 不匹配则丢弃 已防护
重放攻击 录制并重发之前的 RTP 包 第6层: SRTP 滑动窗口 128 包滑动窗口检测并丢弃重放包 已防护
DTLS 中间人 拦截 DTLS 握手，替换自己的证书 第5层: SDP 指纹 伪造证书的 SHA-256 指纹与 SDP 中传递的不匹配 已防护
TURN 中继窃听 在 TURN 服务器上抓包 第6层: SRTP TURN 只转发已加密的 SRTP 包，无法解密 已防护

当前风险点

风险根因影响攻击场景优先级
板端 VERIFY_OPTIONAL CA 证书不完整 信令层中间人攻击 攻击者伪造 LiveKit Cloud 证书，板端不验证 → 窃听/篡改信令 → 替换 SDP 指纹 → 解密全部媒体 P0
DTLS Cookie 禁用 简化实现 DTLS 放大攻击 攻击者伪造源 IP 发送 ClientHello，板端响应大量数据到受害者 IP P0
JWT 在 URL 中 WebSocket 不支持 Header Token 泄露到日志 服务器日志/CDN 缓存记录了 access_token，泄露后可在 exp 内使用 P1
证书签名 SHA-1 KVS 默认值 理论碰撞风险 SHA-1 已被证明可碰撞，但 DTLS 证书由 CTR-DRBG 随机生成，实际碰撞概率极低 P1
TURNS 失败 缺 CA 证书 TURN 只能用明文 UDP TURN 服务器与板端之间无 TLS，中间人可观察到 TURN 流量（但内容仍是 SRTP 加密） P2
嵌入式随机数质量 启动早期熵不足 密钥可预测 设备刚启动时 /dev/urandom 熵不足，此时生成的密钥可能可预测 P2
最危险的风险链

VERIFY_OPTIONAL → 替换 SDP 指纹 → DTLS 中间人 → 获取 SRTP 密钥 → 解密全部视频。这是一条完整的攻击链，从第2层的弱点一直穿透到第6层。修复 VERIFY_OPTIONAL（推送 CA 证书 + 改 VERIFY_REQUIRED）是最高优先级。

量产安全建议

优先级建议工作量修复的攻击
P0 推送完整 CA 证书到板端，TLS 改为 VERIFY_REQUIRED 0.5 天 信令层中间人攻击 → 全链路攻破
P0 启用 DTLS Cookie (HelloVerifyRequest) 1 天 DTLS 放大/重放攻击
P1 JWT 通过 header 或 body 传递，而非 URL query 0.5 天 Token 泄露到服务器日志
P1 证书签名算法从 SHA-1 改为 SHA-256 改 1 行 理论上的 SHA-1 碰撞攻击
P2 TURNS (TURN over TLS) 启用 跟随 P0 TURN 链路元数据泄露
P2 JWT 短有效期 + 自动刷新 (TokenUpdate, tag=11) 1 天 Token 泄露后的影响窗口
P2 验证板端 /dev/urandom 启动各阶段熵质量 需测试 低熵导致密钥可预测

安全增强后的完整链路

修复后的安全链路: API Secret (后端) → JWT (HMAC-SHA256 签名, 短有效期, 通过 header 传递) → WSS (TLS 1.2, ECDHE, VERIFY_REQUIRED ✓, ALPN http/1.1) → ICE (STUN HMAC-SHA1, TURN 长期凭证, TURNS ✓) → DTLS (ECDHE, ECDSA P-256, Cookie ✓, SHA-256 签名 ✓) → SDP 指纹 (SHA-256, TLS 保护 ✓) → SRTP (AES-128-CTR + HMAC-SHA1-80, 重放防护) 每层都安全 → 整条链路安全 ✓
